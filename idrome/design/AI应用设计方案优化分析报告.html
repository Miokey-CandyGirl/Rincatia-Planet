3.4 暂不采纳项

暂不采纳：迁移至轻量框架（Preact / Alpine.js）
评估报告建议考虑迁移至 Preact 或 Alpine.js。但本项目作为琳凯蒂亚文化社区的独立子应用，采用原生 HTML/CSS/JS 是与词典 PWA 一致的既定技术选型，且 public/idrome/ 为静态部署目录，引入框架将增加构建复杂度。替代方案：引入 ES Modules 原生模块化 + Proxy-based 响应式状态管理，在不增加构建工具的前提下提升可维护性。
暂不采纳：Supabase Realtime 强制多设备同步
评估报告建议明确多设备实时同步保障机制。当前方案以 localStorage storage 事件实现跨标签页同步，多设备同步依赖用户主动刷新。强制 Realtime 会增加 Supabase 连接数和复杂度。替代方案：在设置面板中提供"实时同步"开关，用户按需开启。

4优化需求清单（优先级排序）

基于匹配度分析，提出以下 12 项优化需求，按优先级 P0（必须）→ P1（高）→ P2（中）→ P3（低）排序。每项包含必要性、可行性及预期效益分析。

1 启动前 API 可行性验证 P0 必须
对应风险：技术假设未验证（高风险） 影响维度：可行性 (7.0) 预计工作量：1-2 天

必要性

  • DeepSeek V4-Flash 为 2026 年 4 月新模型，thinking 参数格式、reasoning_content 字段结构、Vision 能力均基于文档描述，未经实际调用验证
  • 百度 AI 搜索 API 的端点路径和计费方式未完全确认
  • 豆包 ASR/TTS/文档解析 API 的调用方式可能与方案描述存在差异
  • 若 API 实际行为与文档不符，深度思考、流式解析、语音、OCR 等核心模块需返工

可行性

  • 使用独立 Node.js / Deno 脚本逐一调用各 API，验证请求/响应格式
  • 验证项：DeepSeek thinking 模式 SSE 结构、百度搜索端点、豆包 ASR PCM 格式、js-tiktoken 对 DeepSeek 的估算精度
  • 无前端依赖，可在开发前独立完成

预期效益

  • 消除最高风险项，避免开发后期核心模块返工
  • 验证结果可直接修正设计方案中的 API 调用代码
  • 为后续 Mock 层建立提供真实响应样本
2 引入 ES Modules 原生模块化 + Proxy 响应式状态管理 P0 必须
对应风险：无框架可维护性（高风险） 影响维度：可扩展性 (7.5)、技术实现难度 (6.5) 预计工作量：2-3 天

必要性

  • 17 个 JS 模块使用全局变量组织（chatState、apiRouter、KnowledgeLoader 等），状态散落难以追踪
  • DOM 操作与数据状态手动同步，容易产生不一致
  • 新增功能时代码组织困难，重复代码多

可行性

  • 使用浏览器原生 ES Modules（<script type="module">），无需构建工具
  • 引入 Proxy-based 响应式状态管理（约 50 行代码的轻量 Store 实现）
  • 将全局变量改为 export / import 模块化组织
  • 与 public/idrome/ 静态部署完全兼容

预期效益

  • 状态变更自动触发 UI 更新，消除手动 DOM 同步
  • 模块化后代码可维护性显著提升
  • 为后续功能扩展（对话导出、分享等）奠定架构基础

实现示例

// store.js — 轻量响应式状态管理
export function createStore(initialState) {
  const listeners = new Set()
  const state = new Proxy(initialState, {
    set(target, key, value) {
      target[key] = value
      listeners.forEach(fn => fn(target))
      return true
    }
  })
  return {
    state,
    subscribe(fn) { listeners.add(fn); return () => listeners.delete(fn) }
  }
}
3 关键第三方库本地化 P1 高
对应风险：CDN 国内访问稳定性（中风险） 影响维度：可行性 (7.0)、用户体验 (8.5) 预计工作量：0.5 天

必要性

  • Supabase JS SDK、marked.js、DOMPurify、KaTeX 为核心依赖，CDN 不可达时应用完全不可用
  • 中国内地访问境外 CDN 不稳定，首次访问体验可能受影响
  • Service Worker 缓存仅在首次成功加载后才生效

可行性

  • 下载 4 个核心库到 public/idrome/assets/vendor/ 目录
  • HTML 中优先加载本地路径，onerror 回退到 CDN
  • 非关键库（highlight.js、SheetJS、PDF.js）保留 CDN + 回退策略

预期效益

  • 消除首次访问的 CDN 不稳定性风险
  • Service Worker 缓存策略更可控（同源缓存）
  • 加载速度提升（减少 DNS 解析和 TLS 握手）

7综合结论

总体判定

经系统性分析，iDrome AI 应用设计方案需要依据评估报告进行优化。当前方案综合得分 8.2/10（B+），在功能性和创新性方面表现优秀，但在可行性（7.0）、技术实现难度（6.5）方面存在明显改进空间。通过实施 12 项优化措施，预计综合得分可提升至 9.02/10（A-），3 项高风险项可全部降级。

优化必要性总结

12 项优化需求中，P0 必须项 2 项（API 验证 + 架构模块化）是开发前的必要准备，直接影响核心功能能否正常工作；P1 高优先级 3 项（库本地化 + 注入防护 + Mock 测试）是核心开发阶段的加固措施；P2 中优先级 5 项是功能完善和体验优化；P3 低优先级 2 项是收尾增强。

项目框架兼容性

所有优化措施均严格在 public/idrome/ 目录下执行，与主网站（Vue 3）、DromAI（React）、Supabase 后端完全兼容。ES Modules + Proxy 状态管理方案无需引入构建工具，与 public/idrome/ 的静态部署模式一致。Edge Function 新增（shared_conversations 表、文件安全扫描、Embedding 检索）在 supabase/functions/ 下独立开发，不影响主网站已有的 send-sms 和 verify-sms 函数。

实施建议

建议严格按五阶段路径推进：阶段 0（验证与架构准备）必须在正式开发前完成，是后续所有工作的基础；阶段 1-4 与设计方案原有的六阶段实施规划对齐，在每个阶段完成对应优化项。每阶段完成后进行评审，根据实际验证结果调整后续方案。

最终结论

该设计方案具备实施条件，推荐在完成阶段 0 优化后启动正式开发。评估报告提出的核心风险（API 验证、架构可维护性、外部依赖）均有明确的优化对策，且优化措施与项目框架完全兼容。通过系统性优化，iDrome 有望成为琳凯蒂亚文化社区的高品质 AI 应用。
